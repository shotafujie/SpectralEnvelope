# ADR-0001: 分解・再合成をブラウザ内（Web Worker）で行い、WORLD 本家を自前で WASM ビルドする

## ステータス

Proposed

## 日付

2026-09-18

## 関連ロードマップ項目

なし（`docs/roadmap.md` は未作成）。狙いは「GitHub Pages に置くだけで誰でも試せる」こと。

## コンテキスト

### 解決したい課題

v0.1.0 は、分解と再合成を Python サーバー（`jig/server.py`、pyworld）で行っている。音声の変換には ffmpeg も使う。
そのため GitHub Pages のような静的ホスティングに置いても動かない。
試すにはリポジトリを clone し、Python 環境と ffmpeg を用意する必要があり、音声に詳しくない人に渡せない。

### 現時点の数値（`docs/research/wasm-spike.md`、Apple M4 Max、Node 22、合成母音、5 回の中央値）

| 項目 | 3 秒（601 フレーム） | 10 秒（2001 フレーム、v0.1.0 の上限） |
|---|---|---|
| 分解（ネイティブ pyworld） | 0.47 秒 | — |
| 分解（WASM） | 0.73 秒 | **2.06 秒** |
| 再合成（WASM） | 0.041 秒 | 0.12 秒 |
| WASM ヒープ（1 件を作業中） | 23MB | 87MB（`ALLOW_MEMORY_GROWTH` で広げたヒープは縮まない） |
| sp / ap の 1 件あたりの保持量（Float64） | 9.9MB | 32.8MB |
| 10 件保持（Float64 / Float32） | 94MB / 47MB | 328MB / 164MB |

- WASM とネイティブ（pyworld 0.3.5）の出力の差は、最大でも 1.2e-11
- 無加工往復の包絡差は、どちらも 0.25dB
- sp / ap を Float32 に落として合成しても、包絡差は 0.25dB のままで、再合成音の差は最大 9.8e-9
- 成果物は `.wasm` 100KB と読み込み用の `.js` 8KB
- 分析条件は frame_period 5ms、fft_size 2048、44.1kHz モノラルで固定

### 制約・既存資産

- v0.1.0 は 5 アイテム・149 仕様・テスト 238 件がすべて PASS し、独立検証も済んでいる（`ce54387`）
  - テストの内訳: Python のユニット・統合テストが約 140 件、E2E（Playwright、`tests/e2e/`）が 102 件
  - E2E は `jig/server.py` を実際に起動し、`/api/*` への要求を観測点にしている（応答を待つ、要求を保留する、件数を数える）
- 149 仕様のうち約 70 件が HTTP API（`/api/analyze` `/api/synthesize` `/api/envelope` など）を前提にしている
- v0.1.0 の上限: 録音は 10 秒（`MAX_SAMPLES`、SPEC-010）、保持は 10 件（`MAX_ENTRIES`）
- DSP は Python（NumPy と `scipy.fft.dct`）で書かれている。再合成の経路（`jig/server.py` の `synthesize()`）は次の処理からなり、JS への移植が必要
  - `apply_params()` の中: formant / smooth / tilt / bands / curve / morph
  - `apply_params()` の外: モーフ相手の伸縮（`stretch_partner`）、`f0 * pitch`、長さの切り詰め、表示用の dB 変換（`to_db`）、パラメータのクランプ
- 開発者は 1 人。ビルド環境として Docker と `emscripten/emsdk` イメージがある
- 実機で計測できるのは Mac（Chrome / Safari）と Pixel（Android の Chrome）。iPhone は無い

### 前提としている未確定事項

- ブラウザでの速度とメモリ。測ったのは Node だけ
- 実際の声（合成母音以外）での挙動
- DSP を JS に移したときの速度（DCT-II を FFT ベースで書く前提）

## 検討した選択肢

### 選択肢 A: 現状維持（Python サーバーを Python が動くホストに置く）

- 概要: `jig/server.py` を Render / Fly.io などの PaaS に置き、Pages は使わない
- メリット: コードの変更がほぼ無い。149 仕様とテスト資産がそのまま使える。速度もネイティブのまま
- デメリット: ホスティング費用と運用（スリープからの復帰待ち、ffmpeg 入りのイメージ管理）が発生する。録音データが利用者のブラウザから第三者のサーバーへ送られる。公開サーバーとしての入力検証・容量制限・濫用対策が新たに必要になる

### 選択肢 B: Pages + 手元のサーバー

- 概要: UI だけを Pages に置き、分解と再合成は利用者が手元で起動した `jig/server.py` を呼ぶ
- メリット: 変更が少ない
- デメリット: 利用者が Python と ffmpeg を用意する必要は結局残り、課題が解決しない。HTTPS のページから `http://localhost` を呼ぶことになり、混在コンテンツと CORS の扱いも必要になる

### 選択肢 C1: ブラウザ内で完結させ、WORLD は World.JS を使う

- 概要: 既存の Emscripten ラッパー World.JS（MIT）を依存として取り込む
- メリット: 自分でビルドする手間が省ける
- デメリット:
  - 2019 年から更新が止まっていて、README 自身が「obsolete かもしれない」と書いている
  - 関数のシグネチャ、メモリの扱い、Float32 / 64 のどちらかが文書化されていない
  - ベースにしている WORLD のリビジョンが pyworld と一致する保証が無い。Python 版をゴールデンデータにする戦略（後述）が成り立つか分からない
  - ビルド時の最適化フラグも選べない

### 選択肢 C2: ブラウザ内で完結させ、WORLD 本家を自前で WASM ビルドし、DSP は JS に移植する

- 概要: `mmorise/World` の `d625e76` を固定し、必要な関数だけを公開する薄い C ラッパー（約 40 行）と一緒に `em++ -O3` でビルドする。DSP は JS に書き直す
- メリット:
  - スパイクで、pyworld との一致（1e-11）、速度、サイズ（108KB）を確認済み
  - 公開 API を自分で決められる
  - 更新の止まった依存を抱えずに済む。WORLD 本体は 2025 年以降ほぼ更新が無く、追従の負担は小さい
- デメリット:
  - ビルド環境が要る（ADR-0002）
  - C ラッパーの保守を自分で持つ
  - DSP を JS に移植する作業と、移植の正しさを確かめる仕組み（ゴールデンデータ）が要る

### 選択肢 C2': WORLD は C2 と同じく自前ビルド、DSP は Pyodide 上で Python のまま動かす

- 概要: `jig/server.py` の DSP 関数を、ブラウザ内の Python（Pyodide）でそのまま動かす
- メリット: DSP を移植しなくてよく、実装は 1 系統のまま。ゴールデン一致テストも要らない
- デメリット:
  - 初回に読み込む量が約 29MB になる（Pyodide v314.0.7 の実測で、`pyodide.asm.wasm` 9.6MB、標準ライブラリ 2.5MB、numpy 3.0MB、scipy 14.0MB）。C2 は 108KB
  - Pyodide の起動（Python ランタイムの初期化とパッケージの読み込み）に数秒かかる見込み（未実測）
  - 「誰でも試せる」ことが狙いで、特にスマートフォンの回線で開かれたときに、この読み込みが最初の体験を大きく損なう
  - WORLD（WASM）と Python（Pyodide）の 2 つのランタイムの間で、sp / ap を受け渡す仕組みも要る

### 選択肢 C3: ブラウザ内で完結させ、WORLD を JS / TypeScript に手で移植する

- 概要: C++ 約 7300 行のうち、harvest / cheaptrick / d4c / synthesis と依存部分を JS に書き直す
- メリット: ビルド工程が無くなる。デバッグをブラウザの開発者ツールで完結できる
- デメリット: 移植量が大きく（数千行）、1e-11 レベルの一致は期待できない。FFT も自前で用意する必要がある。速度は WASM より遅くなる見込み。移植の誤りを探す手間に見合う利点が無い

## 決定

**選択肢 C2 を採用する。** あわせて次を決める。

### 1. 状態は Worker が持つ

- 分解・DSP・再合成は、すべて 1 つの Web Worker 内で行う
- v0.1.0 の `Store` に相当する状態（分解結果の保持と LRU による追い出し）も Worker が持つ
- メインスレッドが受け取るのは次のものだけ:
  - 分解結果の id
  - 描画に要るデータ（波形、1 フレーム分の dB 列、有声フレームの一覧など）
  - 再合成した音声
- sp / ap はメインスレッドへ渡さない。v0.1.0 の `/api/envelope` が 1 フレーム分だけを返す設計と同じ形にする
- つまみ操作などで要求が続けて届いたときは、最新の 1 件だけを処理し、古い要求は捨てる

これにより、エンジンの仕様は 2 層に分けて書ける。Worker 内の純粋な関数の仕様と、メインスレッドとのメッセージの仕様である。

### 2. 上限は v0.1.0 と同じ（録音 10 秒・保持 10 件）。分解中は進捗を表示する

10 秒の分解は M4 Max の Node でも 2.06 秒かかり、HANDOFF の目安（2 秒未満）をわずかに超える。
上限を下げずに、分解が Worker で動いている間は進捗を表示して待ち時間を許容する。

### 3. 計算は Float64 で行い、保持するときだけ Float32 にする

- WORLD と DSP の計算は Float64 で行う
- 分解結果の sp / ap は、保持するときに Float32 に落とす。10 秒 × 10 件で 164MB になり、目安の 200MB に収まる
- f0 と時刻の列は Float64 のまま保持する（小さいため）
- **v0.1.0 との差として明示する**: 保持の段階で丸めるので、再合成の出力は v0.1.0 と完全には一致しない。スパイクでは、再合成音の差は最大 9.8e-9、無加工往復の包絡差は変わらなかった（0.25dB）

### 4. 移植の正しさは、Python 版から作ったゴールデンデータで確かめる

- **範囲**: 入力（44.1kHz モノラルの Float64 配列）と params から、`synthesize()` が出す音声 y と、`/api/envelope` に相当する出力（dB 列）まで
  - 「DSP の途中まで」ではなく、再合成の経路全体を対象にする。伸縮、pitch、長さの切り詰め、クランプもすべて含む
  - 保持のときの Float32 化（決定 3）は、ゴールデンデータを生成する側でも同じように行う
- **データ**: ゴールデンデータは生成物としてリポジトリにコミットする。生成に使った numpy / scipy / pyworld のバージョンも一緒に記録する。JS 側のテストは、このファイルを読むだけで Node の中で完結させる（Python も Docker も要らない）
- **許容誤差**: dB 列は、既存の SPEC-037 / SPEC-404 に合わせて「dB 換算で 1e-6 以内」とする。y の許容誤差は、006 アイテムの仕様で決める
- **寿命**: Python との一致テストは、DSP の移植（006 アイテム）が終わった時点で凍結する
  - 以後、Python の実装は更新しない
  - その時点のゴールデンデータを、JS 版の回帰テストの基準として残す
  - 新しい DSP 機能や挙動の変更は、JS の仕様とテストだけで検証する。先に Python で実装することはしない

### 5. ビルドの入力をすべて固定する

- 固定するもの: WORLD のリビジョン（`d625e76`）、ビルドオプション、emsdk イメージのダイジェスト（詳細は ADR-0002）
- 変えるときの条件: ゴールデンデータとの一致テストを通すこと
- 速度の基準値（Node、3 秒と 10 秒の入力、分解と再合成の中央値）を `benchmarks/` に置く。再ビルドしたら、基準値の 1.5 倍以内であることを確かめる

### 6. 移行は段階的に行う

- **エンジンのアダプタ**: `index.html` とエンジンの間に、差し替えられる境界を置く
  - 移行している間は、UI が HTTP 実装（v0.1.0 のサーバー）と WASM 実装のどちらでも動く状態を保つ
  - E2E テストは、ネットワーク要求の代わりにこの境界で、呼び出しを記録したり保留したりする
- **仕様**:
  - HTTP API を前提にした旧仕様は「v0.1.0 の Python 参照実装の仕様」として凍結し、書き換えない
  - 新しい仕様は `docs/items/006-wasm-engine/` に SPEC-700 以降で起こし、旧 SPEC から新 SPEC への対応表を 006 の spec に置く
  - 同じ TC-ID を 2 系統で使わない。JS 側のテストには新しい TC-ID を振る
- **Python 版の扱い**:
  - `jig/server.py` と Python のテストは、移行が終わるまで動く状態で残す（HTTP 実装として並べて動かす相手でもあるため）
  - 移行が終わった後に HTTP 層を main から外すかどうかは、006 の完了時に判断する。v0.1.0 のサーバー版は、タグ `v0.1.0` からいつでも取り出せる

### 7. 仕様策定（Phase 2）の前に実機で計測し、撤退条件で判定する

計測用のページを作り、次の端末で 3 秒と 10 秒の分解時間、再合成の時間、タブのメモリを測る。

- Mac の Chrome と Safari
- Pixel の Chrome

初回の実行と中央値は分けて記録する。

| 指標 | 合格の目安 | だめなら |
|---|---|---|
| Mac（Chrome / Safari）で 3 秒を分解する時間 | 2 秒未満 | ビルドの最適化オプションを見直す。それでもだめなら A 案に戻る |
| Pixel で 3 秒を分解する時間 | 6 秒未満 | 上限を短くする、または harvest を dio に替えることを検討する（どちらも v0.1.0 の仕様変更になるので、別の ADR にする） |
| Pixel で 10 秒の録音を 10 件保持する | タブが落ちない | 保持件数を減らす |

iOS は計測できないので、動作を保証しない。

**理由**: 課題は「静的ホスティングだけで誰でも試せる」ことで、A と B はこれを解かない。

C 系の中では、C2 だけが Python 版とのビット単位に近い一致を実測で確かめられている。移植の正しさを、すでに検証済みの実装に紐付けられるのも C2 だけである。
C1 の利点は「ビルドの手間が省ける」ことだけだが、スパイクでその手間は小さいと分かった（ラッパー 40 行・コマンド 1 本）。

C2' は移植の手間を無くせる。しかし初回の読み込みが C2 の約 270 倍（29MB と 108KB）になり、「誰でも気軽に試せる」という狙いに反する。

DSP を二重に持つ負担は、ゴールデンテストに寿命を設けること（決定 4）で、移植の期間だけに限定する。

## 影響

- 約 70 件の HTTP API 前提の仕様に対し、「エンジン関数」と「Worker とのメッセージ」の仕様を新しく書く（006 アイテム、SPEC-700 以降）
  - 移す TC は、Python 側の約 140 件と E2E の 102 件
  - E2E はネットワーク要求ではなくアダプタを観測するように書き直す。仕様のうち「要求をまとめる」「応答待ちの間は操作を無効にする」（SPEC-201〜203 など）は、「エンジン呼び出し」の観点で書き直す
- ffmpeg が不要になる。入力の音声は `decodeAudioData` と `OfflineAudioContext` で 44.1kHz モノラルに揃える
  - **入力の数値は v0.1.0 と一致しない。** ffmpeg 版は 16bit に量子化していたが、ブラウザ版は Float32 のままで、リサンプリングの実装もブラウザごとに違う。互換は保証しない
  - デコード部分は別の仕様として立て、許容する差（例: 包絡差の上限）をそこで決める
  - 10 秒で切り詰める処理（SPEC-010 相当）は、デコードの直後、Worker に渡す前に行う
  - ゴールデンテストは「44.1kHz モノラルの Float64 配列」を起点にするので、デコードの差に影響されない
- 録音データがブラウザの外に出なくなる（サーバーへの送信が無くなる）
- 速度はブラウザと端末に依存するようになる。決定 7 の計測で、撤退するかどうかを判定する
- 10 秒の分解を一度行うと、WASM のヒープは 87MB まで広がり、その後も縮まない。保持分（最大 164MB）と合わせて、タブのメモリは 250MB 前後になる見込み。決定 7 の Pixel での計測で確かめる
- リポジトリに JS / WASM と Python の 2 系統が並ぶのは、移行が終わるまでの間だけとする（決定 4・6）
- DSP の JS 移植の速度は測っていない。全フレームの処理は再合成のときだけで、つまみ操作で走るのは 1 フレーム分の計算だけなので、体感への影響は限られる見込み。遅ければ、DSP も C で書いて同じ WASM に入れる案を検討する

## レビュー記録

- 観点: 性能 / 移行 / 複雑性（2026-09-18）
- 主な指摘と対応:
  - [Major] 10 秒の録音で、メモリと速度の目安を超える（性能） → 10 秒で実測した（分解 2.06 秒、10 件保持で 328MB）。ユーザーの判断で、上限は変えず進捗を表示すること（決定 2）、保持は Float32 にすること（決定 3）にした
  - [Major] ブラウザで測っておらず、撤退条件が無い（性能・移行） → 決定 7 を追加した。計測する端末は、ユーザーの手元にある Mac と Pixel。iOS は保証外にする
  - [Major] Worker とメインスレッドの境界、状態を持つ場所が決まっていない（性能・複雑性） → 決定 1 を追加した。状態は Worker が持ち、最新の要求だけを処理する
  - [Major] 性能の劣化に気づけない。emsdk のバージョンが固定されていない（性能） → 決定 5 で、ダイジェストの固定と `benchmarks/` の基準値を加えた
  - [Major] DSP を二重に持ち続ける規則が無い（複雑性） → 決定 4 で、ゴールデンテストの寿命を決めた
  - [Major] Pyodide で DSP を動かす案が比較されていない（複雑性） → 選択肢 C2' を追加し、読み込み量の実測値（29MB）を理由に却下した
  - [Major] E2E 102 件の移行経路が無い（移行） → 決定 6 で、エンジンのアダプタを置くことにした。E2E はアダプタを観測する
  - [Major] 切り替えの段取りと戻る地点が無い（移行） → 決定 6 で、アダプタを使って HTTP 版と並べて動かすことにした。戻る地点は決定 7 の撤退条件にした
  - [Major] 旧仕様と旧 TC の扱いが衝突している（移行） → 決定 6 で決めた。旧仕様は凍結し、新しい仕様は SPEC-700 以降に起こして対応表を置く。TC-ID は重複させない
  - [Major] ゴールデンデータの範囲が狭く、生成環境も許容誤差も決まっていない（移行） → 決定 4 で、範囲を再合成の経路全体に広げた。データはコミットしてバージョンを記録する。許容誤差は dB 換算で 1e-6 とした
  - [Minor] 入力のデコードで v0.1.0 との互換が崩れる（移行） → 影響に明記した
  - [Minor] HTTP 層のテストと Python 版 UI の扱い（移行・複雑性） → 決定 6 で、移行が終わるまで残し、完了時に判断することにした
  - [Minor] テストに 3 つのツールチェーンが要る（複雑性） → 決定 4 で、JS のテストは Node だけで完結させることにした
  - [Minor] DSP の JS 移植の速度、ブラウザでの初回実行（性能） → 影響と決定 7（初回と中央値を分けて記録する）に反映した
