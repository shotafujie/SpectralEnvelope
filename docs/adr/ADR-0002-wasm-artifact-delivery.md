# ADR-0002: WORLD の WASM 成果物をリポジトリにコミットし、照合に通ったコミットだけを配信する

## ステータス

Proposed

## 日付

2026-09-18

## 関連ロードマップ項目

なし（`docs/roadmap.md` は未作成）。ADR-0001（ブラウザ内で WORLD を動かす）の続き。

## コンテキスト

### 解決したい課題

ADR-0001 で、WORLD 本家を自前で WASM にビルドすることにした。
GitHub Pages で配信する以上、ビルドした `world.wasm` と読み込み用の `world.mjs` がどこかに存在する必要がある。
ビルドには Docker と `emscripten/emsdk` イメージ（3.35GB）が要る。これが無い環境（別のマシン、CI、将来の協力者）でどう扱うかを決める。

守りたいのは、**配信されているバイナリが、リポジトリにあるソースから作られたものだと言えること**。
ラッパーを直したのに再ビルドを忘れた、手元の環境がおかしかった、といった場合に、それと気づかず別物を配信しないようにしたい。

### 現時点の数値

| 項目 | 値 |
|---|---|
| 成果物サイズ | `world.wasm` 100,043 バイト + `world.mjs` 8,317 バイト |
| ビルド時間 | 数秒（イメージ取得済みの場合） |
| emsdk イメージ | 3.35GB。`latest`（emcc 6.0.9）。インデックスのダイジェストは `sha256:96617f27…63cc`。その中の linux/arm64 は `sha256:41039722…c7d4`、linux/amd64 は `sha256:3ba391c5…74b5` |
| WORLD のソース | `d625e7608ca23a870018f01e7c562ac683d9847f`（2025-02-21）。`src/` は .cpp と .h を合わせて 8456 行、332KB。修正 BSD ライセンス |
| 成果物が変わる契機 | WORLD のリビジョン変更、C ラッパーの変更、emcc のバージョン変更、ビルドオプションの変更。WORLD 本体は 2025-02 以降更新が無い |

### 再現可能ビルドの確認（2026-09-18）

- **同じプラットフォーム・同じイメージでは、バイト単位で一致した。** linux/arm64 のイメージで出力先を変えて 3 回ビルドし、`world.wasm`（`929c6a5e…1926`）と `world.mjs`（`55e51540…6d95`）の SHA-256 がすべて一致した
- **プラットフォームをまたいだ一致（arm64 と amd64）は確かめていない。** LLVM のバイナリが別物なので、一致する保証は無い

### 制約

- 開発者は 1 人。main へローカルでマージして push する運用で、PR は通していない
- リポジトリは GitHub で公開済み。GitHub Actions はまだ使っていない（`.github/` なし）
- 公開リポジトリなので、GitHub の arm64 ホステッドランナー（`ubuntu-24.04-arm`）が使える
- E2E テスト（Playwright）はローカルで実行している

## 検討した選択肢

### 選択肢 A: 何もしない（成果物は持たず、使う人がそれぞれビルドする）

- 概要: ビルド手順だけを README に書き、成果物は gitignore する
- メリット: 生成物がリポジトリに入らない
- デメリット: Pages で配信できず、ADR-0001 の目的が果たせない。clone した人は Docker と 3.35GB のイメージが無いと動かせない

### 選択肢 B: 成果物をリポジトリにコミットし、ブランチの中身をそのまま配信する

- 概要: `world.wasm` と `world.mjs` をコミットし、Pages は「ブランチから配信」にする
- メリット: 最も単純。clone すれば Docker 無しで動き、テストも回せる。成果物は 108KB と小さく、変わる頻度も低いので、履歴の肥大化は問題にならない
- デメリット: コミットされた成果物が、コミットされたソースから本当に作られたものか保証されない。ラッパーだけ直して再ビルドを忘れると、気づかないまま古いバイナリが配信される

### 選択肢 B': B に入力ハッシュのスタンプを加える

- 概要: ビルド時に、ビルドの入力（ラッパー、ビルドスクリプト、WORLD のソース、イメージのダイジェスト）のハッシュを、成果物の横のスタンプファイルに書き出す。テストの前段で「今の入力のハッシュ ＝ スタンプ」を確かめる
- メリット: Docker もイメージも要らず、再現可能ビルドを前提にしない。ローカルのテストで、CI を待たずに再ビルド忘れに気づける
- デメリット: 検査しているのは「スタンプと入力の対応」だけで、「スタンプと成果物の対応」は検査していない。成果物だけが差し替わった場合や、スタンプを手で書き換えた場合は検出できない。配信を止める仕組みも持たない

### 選択肢 C: CI（GitHub Actions）でビルドし、デプロイ時に焼く（コミットしない）

- 概要: 成果物は gitignore し、Pages へのデプロイ時に Actions でビルドする
- メリット: 配信物は常にソースから作られる。ソースと成果物のずれが原理的に起きない
- デメリット: ローカルでテストや UI を動かすにも、Docker とビルドが必須になる（clone しただけでは動かない）

### 選択肢 D: 成果物をコミットし、CI でソースから再ビルドして一致を確かめ、通ったコミットだけを配信する

- 概要: B と同じく成果物をコミットする。加えて Actions で、固定したプラットフォームとイメージで再ビルドする。コミット済みの成果物とバイト単位で一致しなければ失敗させ、配信もしない
- メリット: B の手軽さ（clone すれば動く）を保ったまま、配信されるバイナリそのものがソースと一致することを保証できる
- デメリット: ビルドが再現可能であることが前提になる（同じプラットフォームでは確認済み）。Actions の設定を保守する必要がある。CI の実行ごとにイメージを取得する

## 決定

**選択肢 D を採用する。** 具体的には次のとおり。

1. **ビルドの入力はすべてリポジトリの中に置く**
   - WORLD の `src/` を `third_party/world/` にベンダリングする。ライセンス文と、取り込んだ 40 桁のコミットハッシュ（`d625e7608ca23a870018f01e7c562ac683d9847f`）も一緒に置く
   - C ラッパー
   - ビルドスクリプト。emcc のオプション、コンテナ内のマウント先、出力先を、このスクリプト 1 か所にまとめて固定する
2. **ビルドするプラットフォームを linux/arm64 の 1 つに固定する**
   - イメージはアーキテクチャ別のダイジェスト（`sha256:41039722…c7d4`）で指定し、タグ指定は認めない
   - CI は arm64 ランナー（`ubuntu-24.04-arm`）で動かす。手元（Apple Silicon）と CI で同じイメージが動くので、プラットフォームをまたいだ一致を期待する必要がなくなる
3. **成果物 `world.wasm` と `world.mjs` をコミットする**
4. **照合に通ったコミットだけを配信する**
   - Pages の配信元を「GitHub Actions」にする
   - デプロイジョブは照合ジョブの成功を条件にする（`needs:`）
   - 配信するのは、照合で一致を確かめたコミット済みの成果物
5. **同じプラットフォームでも一致しなくなった場合は、選択肢 C に切り替える**
   - 例: emsdk を更新したら非決定的な出力になった
   - 配信物は CI でビルドしたものにする。コミット済みの成果物は、ローカル開発用の扱いに格下げする
   - ゴールデンデータとの一致テスト（ADR-0001 決定 4）は、この照合の代わりにしない。あのテストが確かめるのは「正しく計算できること」で、「配信物がソースから作られたこと」ではないから

**理由**: 成果物は 108KB と小さく、変わる頻度も低い。コミットしておけば「clone して開けば動く」状態を保てる。
これは 1 人で開発していて、E2E テストをローカルで回している今の運用に合う。

C は、ずれを原理的に防げる。しかしそのために、日常の開発すべてで Docker を要求するのは割に合わない。

B' は安くて、再ビルド忘れには早く気づける。ただ、配信されるバイト列そのものは保証しないうえに、配信を止める仕組みも持たない。

D の追加の負担は、CI のジョブ 1 本（arm64 ランナーでイメージを取得し、数秒ビルドする）だけ。それで「配信物 ＝ ソースから作られたもの」を保証できる。
再現可能ビルドが成り立つことは同じプラットフォームで確認済みで、プラットフォームを 1 つに固定することで、成り立たないかもしれない分岐（arm64 と amd64 の比較）も消せる。

## 影響

- 初めて GitHub Actions を導入する。以後、Actions の設定も保守の対象になる
- main に push しても、照合が失敗すれば配信されない。直接 push の運用のままでも配信は止まるので、ブランチ保護は必須にしない
- emsdk を上げるのは明示的な作業になる。ビルドスクリプトのダイジェストを arm64 のものに書き換え、成果物を再ビルドし、同じコミットに含める。勝手には変わらない
- ラッパーやビルドスクリプトを変更したら、成果物の再ビルドと再コミットを同じコミットに含める必要がある。忘れると照合が失敗し、配信が止まる
- WORLD のソースが上流から消えたり書き換えられたりしても、ビルドには影響しない（ベンダリング済みのため）。WORLD を更新するのは、ソースを差し替える明示的なコミットになる
- ライセンス: WORLD（修正 BSD）の著作権表示とライセンス文を `third_party/world/` に置く。配信物にも、ライセンスの所在が分かるようにする
- Actions の権限:
  - 照合ジョブは `pull_request` と `push` で起動し、`permissions: contents: read` に限る
  - デプロイは別のジョブに分け、main への push のときだけ実行する。`pages: write` と `id-token: write` は、デプロイジョブにだけ与える
  - `pull_request_target` は使わない
  - 外部の action はコミットの SHA で固定する
- キャッシュ: `world.mjs` と `world.wasm` は対で一致している必要がある。更新直後にブラウザのキャッシュで新旧が混ざらないよう、読み込み URL に成果物のハッシュを付ける。読み込んだ成果物のハッシュを console に出して、配信物を特定できるようにする
- 許容するリスク: amd64 のマシン（Intel Mac や x86 の Linux）で手元ビルドすると、成果物が CI と一致しないことがある。そのマシンでは、エミュレーションで arm64 を動かしてビルドする（`--platform linux/arm64`）。開発者は現在 1 人で、使っているのは Apple Silicon だけなので許容する

- 観点: 運用 / セキュリティ / 複雑性（2026-09-18）
- 主な指摘と対応:
  - [Major] 照合がデプロイを止めない（運用・セキュリティ） → 決定 4 を追加。Actions からデプロイし、照合の成功を条件にする
  - [Major] 決定 5 の旧案（ゴールデンテストで代用する）では、配信物の出どころを誰も検証しなくなる（運用・セキュリティ・複雑性） → 決定 5 を書き直した。一致しなくなったら C に切り替え、ゴールデンテストでは代用しない
  - [Major] 正本とするビルド環境が決まっておらず、arm64 と amd64 の比較が矛盾を生む（運用・複雑性） → 決定 2 を追加。プラットフォームを linux/arm64 に固定し、CI も arm64 ランナーで動かす
  - [Major] より単純な B'（入力ハッシュのスタンプ）が検討されていない（複雑性） → 選択肢 B' として比較に加えた。配信物のバイト列を保証せず、配信も止めないので採らない理由を「理由」に書いた
  - [Major] WORLD のソースを取得する方法が信頼境界そのもの（セキュリティ） → 決定 1 でベンダリングに決め、40 桁のハッシュも記録した
  - [Minor] ダイジェストが arm64 専用で CI で使えない（セキュリティ） → 事実確認をした。ADR に書いていた `96617f27…` はマルチアーキテクチャのインデックスのダイジェストで、arm64 専用ではなかった。ただしアーキテクチャごとに中身が別物になる点は正しいので、決定 2 でアーキテクチャ別のダイジェストで固定することにした
  - [Minor] ワークフローの権限（セキュリティ） → 影響に追記した
  - [Minor] glue と wasm がキャッシュで食い違う（運用） → 影響に追記した
  - [Minor] ビルドのパスも再現性の入力になる（複雑性） → 決定 1 で、マウント先と出力先もビルドスクリプトで固定することにした
